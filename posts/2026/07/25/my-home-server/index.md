## はじめに
5年ほど前から自宅サーバーにk8sを導入し、Mastodon、Discord Bot、このブログ、自作Webサービスや各種アプリケーションをKubernetes上で動かしています。
1ヶ月ほど前に、マニフェストリポジトリをほぼ全て公開リポジトリに移行したため、内容を備忘録として書きます。

## ハードウェア構成
ハードウェアはVPS 1台と、自宅内の3台の物理マシンの計4ノードで構成されています。

### ノード構成
| ノード名 | 役割 |
| --- | --- |
| `can` | control plane | ConoHa VPS 2GBプラン |
| `cope` | worker | 自宅（ミニPC） |
| `mmsan` | worker | 自宅（ミニPC） |
| `saba` | worker | 自宅（Raspberry Pi 4） |

学割が使えなくなる3月にMac Miniの最小構成を買ったので追加する予定なのですが、めんどくさくて放置中です。また、CPUが極端に弱いノードがあると他の不安定になる(特に後述するLonghorn)ので、ラズパイノードはそろそろ消したいですね。

### VPSをコントロールプレーンにする理由
自宅回線の契約プランがv4 over IPv6なため、外部に固定のIPv4アドレスを割り振ることができません。このため、グローバルIPv4アドレスを占有できる外部のVPSをコントロールプレーン（およびリバースプロキシのエントリーポイント）として利用し、外部からのトラフィックをVPS経由で自宅のワーカーノードへルーティングする構成をとっています。

まあ、VPSはingressのDaemonSetだけ動かすワーカーノードにしても問題なく動きますが、色々もったいないのでコントロールプレーンとして働いてもらっています。


## ネットワーク構成 (WireGuard)
地理的に離れたVPSと自宅内のマシン群、PCやスマホを1つのLANにするためにWireGuardを使っています。
サーバー間はオーバーヘッドを最小限にするためにフルメッシュで接続しています。スマホやノートPCから接続する時は必ずVPSを経由します。

## Ansibleによるインフラ構築のコード管理
ホストマシンのOS初期設定、ネットワーク（Netplan）、ファイアウォール（UFW）、WireGuard、およびK3sクラスタのインストールは、Ansibleによってコード化されています。(まだ公開リポジトリにできていない)

本当はnixosでやりたいのですが、昔longhorn周りでハマってansibleに移行してから戻れていません。

- **ホスト初期設定**: `open-iscsi`（Longhornストレージの動作要件）や `sysstat` などの必要な基本パッケージを共通でインストールします。
- **NetplanとUFWの自動構成**: VPSと自宅内のネットワーク環境の差異をNetplanテンプレートで埋め、UFWを用いて必要な公開ポート（80/443/SSH、およびMinecraftサーバー用のポート等）以外を適切にブロックします。
- **WireGuard鍵の自動ハンドリング**: ノード内で動的にWireGuardの秘密鍵・公開鍵を生成し、マスターとエージェント間で公開鍵を自動で交換して設定ファイル `wg0.conf` を構築します。
- **K3sのインストール・デプロイ**: amd64（x86_64）とaarch64（ARM64）のアーキテクチャ判定を行い、それぞれのホストに適したバイナリを自動ダウンロードします。マスター側で生成されたノードトークンを回収し、エージェント側の引数（`--node-ip` や `--flannel-iface`）にWireGuardのIPを割り当ててクラスタを自動的に立ち上げます。

## 永続ボリューム
永続ボリューム（PV）には、分散ブロックストレージであるLonghornを採用しています。
ノード間で物理ストレージのプールを作り、データの冗長化（レプリケーション）や自動バックアップを実現しています。

### MinIO へのバックアップ
Longhornではバックアップ先としてS3やNFSを設定できます。
ここでは、外部のパブリッククラウドストレージを直接指定するのではなく、同じ k8s クラスタ内にデプロイした S3 互換ストレージであるMinIOをバックアップの宛先して指定しています。これは、S3を指定するとAPIコール数が多すぎて破産するからです。

### rclone による Google Drive への同期
クラスタ内の MinIO にバックアップをとるだけでは、すべてのノードのディスクが同時に故障した際（落雷や災害など）にデータを喪失してしまいます。
そのため、毎日rcloneを用いた同期処理を CronJob で実行し、MinIO 上のバックアップデータを Google Driveに同期しています。

### Longhornの注意点
かなりのCPUとネットワーク帯域を使うため、ラズパイは使わず、同じ物理LANで繋がっている2台のmini pcのみで運用しています。昔はラズパイでも有効化していたのですが、あまりに不安定だったためやめました。

## ネットワークの公開制御とDNS・SSL証明書の自動管理
クラスタ内外に向けたサービスのルーティング、およびDNSとSSL証明書のライフサイクル管理は、**MetalLB**、**Ingress Nginx**、**external-dns**、**cert-manager** の組み合わせによって完全に自動化されています。

### 外部公開用と内部（VPN専用）用の Ingress 分離
サービスへのエンドポイントを提供する Ingress Nginx コントローラーは、意図しないアクセスを防ぐためにパブリック用とプライベート用で2つに分離して運用しています。

1. **`ingress-nginx` (外部公開用)**:
   - コントローラーの Pod を `nodeSelector` によって VPS（`can`）ノードに固定しています。
   - MetalLB を介して VPS の持つパブリックIPアドレス（`163.44.96.193`）を割り当ててバインドしています。これにより、インターネット経由のトラフィックを VPS 上で直接受け取ることができます。
2. **`ingress-nginx-private` (内部・VPN専用)**:
   - ArgoCD の管理画面、Kubernetes Dashboard、各種ツールのダッシュボードなど、外部に露出させたくない管理用サービスのために使用します。
   - 割り当てるIPアドレスとして、後述する WireGuard ネットワーク上のプライベートIPプールを指定しています。これにより、VPN（WireGuard）に接続している端末からしか物理的にアクセスできないセキュアなエンドポイントになります。

### MetalLB による IP アドレスプールの制御
ロードバランサー型 IP の割り当てを行う **MetalLB**（`L2Advertisement`）を用いて、アドレスプールを以下のように定義・制御しています。
- **`default` (自宅ローカルIPプール)**: 自宅LAN内のIP帯（`192.168.11.10 - 30`）
- **`public-ips` (パブリックIPプール)**: VPSのパブリックIP（`163.44.96.193/32`）
- **`local-ips` (VPN専用IPプール)**: 自宅ノード群の WireGuard 内のVPN用IP（`192.168.190.45` や `47`、`53` など）

各 Ingress Nginx サービスの定義で `metallb.universe.tf/address-pool` を使い分けることで、バインド先を動的に切り替えています。

### DNS-01 チャレンジによる SSL 証明書の自動取得 (cert-manager)
SSL/TLS 証明書の自動発行には **cert-manager** を使用しています。
認証プロバイダーには Let's Encrypt を指定していますが、チャレンジ方法に HTTP-01 ではなく Cloudflare API と連携した **DNS-01** を採用しています。
HTTP-01 チャレンジの場合、証明書の検証時に Let's Encrypt サーバーから該当ドメインの 80 番ポートへ HTTP アクセスできる必要がありますが、これは「VPN内からしかアクセスできないプライベートドメイン」では利用できません。DNS-01 チャレンジを利用することで、インターネットから到達不能なVPN専用サービスに対しても、CloudflareのDNSレコードを一時的に自動書き換えして本物の SSL 証明書（HTTPS）を安全に取得・更新できています。

### external-dns による DNS レコードの自動同期
Ingress リソースが追加・削除された際、わざわざ手動で Cloudflare のコントロールパネルを開いて DNS レコードを修正するのは非効率です。
そこで、**external-dns** を導入しています。
`policy: sync` の設定で Cloudflare プロバイダーと連携させており、Ingress のマニフェストが ArgoCD によってクラスタに適用されると自動で DNS レコードが追加され、Ingress が削除されると同時に DNS レコードも同期して自動削除されます。

## GitOps構成 (ArgoCD & Sealed Secrets)
クラスタ内のアプリケーション管理には、ArgoCDを利用したGitOpsを採用しています。
マニフェストリポジトリは [kgtkr/public-cd](https://github.com/kgtkr/public-cd) で公開しています。

### Sealed Secrets による機密情報の管理
リポジトリをパブリックに公開する上で、パスワードやAPIトークンなどの機密情報（Secret）の管理が問題になります。これには `Bitnami Sealed Secrets` を使用しています。
開発者はローカル環境で機密情報を `kubeseal` コマンドで暗号化し、`SealedSecret` カスタムリソースとしてYAMLに変換します。この暗号化データは、クラスタ内にデプロイされたコントローラーの持つ秘密鍵でしか復号できません。そのため、暗号化後のマニフェストは安全に `public-cd` リポジトリへコミットし、一般に公開することができます。

また、`Renovate` をリポジトリに紐付けることで、各種コンテナイメージやHelmチャートのアップデートは自動でPull Requestとして起票されます。スマホからPRをマージするだけで、ArgoCD経由で自動的に本番環境へデプロイが完了します。

また、自作のアプリケーションは全てmasterにプッシュされると [kgtkr/docker-tags-gen-action](https://github.com/kgtkr/docker-tags-gen-action) を使って `20260707061339182-24a45e3` のようなタイムスタンプ付きのタグが付きghcr.ioにプッシュされます。その後、renovateが自動で`public-cd`のイメージタグを更新するPRを投げてくれるので、マージされると自動デプロイされます。
